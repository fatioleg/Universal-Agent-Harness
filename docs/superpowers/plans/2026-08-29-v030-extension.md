# Principle 01: Preserve Sources

## Statement

Original user sources must never be overwritten, silently transformed,
or deleted by any agent action.

## Why this is a principle

Sources are epistemologically authoritative. A derived representation
(markdown summary, embedding, graph node) can be regenerated; a
destroyed source cannot. Anthropic managed-agents makes the same
distinction: "Sources are immutable. Representations are derived.
Summaries are disposable. Graphs are interpretations. Evidence remains
authoritative."

## What it requires

- All agent writes target derived locations (`canonical/`, `derived/`,
  `summaries/`) explicitly named in the project layout.
- The original source directory (`source/`, `inputs/`, or equivalent)
  is read-only by configuration and by permission profile.
- A copy of the original must exist before any transformation begins.

## When this can be overridden

Never. The override protocol (`core/policies/override-protocol.md`)
classifies this principle as non-overridable. The source is the ground
truth; without it, evidence provenance collapses.

## How to verify

- INV-001 lock check in `core/invariants.yaml`.
- Permission profile declares `read` only for the source directory.
- The Bash sensor (planned tool contract `lock-drift-check`) verifies
  no write events target immutable paths.

## Failure mode if ignored

The agent's claim cannot be traced. The evidence ledger records a
pointer to a path that no longer exists. The project cannot survive
a model upgrade, a re-run, or a peer-review challenge.
```

# Principle 02: Maintain Provenance

## Statement

Every material scientific or factual claim must retain an evidence
pointer to a source location and a transformation record.

## Why this is a principle

Böckeler's sensors article and Anthropic's long-running-apps harness
both treat provenance as the link between a claim and the artifact
that justifies it. Without provenance, claims are indistinguishable
from hallucinations. With provenance, claims survive model changes
and reviewer scrutiny.

## What it requires

- The evidence ledger (`core/schemas/extension/evidence-ledger.schema.json`)
  is instantiated for any project with `evidence_burden: scientific`
  or higher.
- Every entry into the ledger records claim_id, source_id,
  source_location, and evidence_type.
- Cross-references between claims and artifacts use stable IDs.

## When this can be overridden

Never. Like preserve-sources, this principle is non-overridable.

## How to verify

- INV-002 lock check in `core/invariants.yaml`.
- Eval EVAL-005 (citation verification) checks claim-source linkage.
- Eval EVAL-009 (conflicting-source resolution) checks that provenance
  disambiguates contradictions.

## Failure mode if ignored

Two agents may make the same claim from different sources and the
project cannot reconcile. A reviewer cannot audit. The output looks
authoritative but cannot be defended.
```

# Principle 03: Least Privilege

## Statement

Effective agent permissions must be limited to the capabilities
required by the approved task. Expansion beyond the universal defaults
requires an explicit human gate.

## Why this is a principle

Anthropic managed-agents describes a structural fix where credentials
are bundled with the resource and never reachable from the agent
sandbox; this prevents prompt injection from extracting tokens.
Hashimoto's adoption story recommends running agents one at a time
and disabling desktop notifications to control context switching.
Both rely on a least-privilege baseline.

## What it requires

- A permission profile (`core/schemas/extension/permission-profile.schema.json`)
  per agent role.
- Universal defaults from `core/universal.yaml` (`delete: denied`,
  `install: denied`, `publish: denied`, `send: denied`, `spend: denied`,
  `merge: denied`).
- Expansion requires recording the decision in
  `core/schemas/extension/decisions.schema.json` with `decided_by: human`.

## When this can be overridden

Overridable per task with explicit human approval recorded in the
decision log. Cannot be silently removed by a more specific layer
(INV-010).

## How to verify

- INV-005, INV-006, INV-010 lock checks.
- The lock file's `permissions` field matches the approved profile.

## Failure mode if ignored

A prompt-injection-style prompt causes the agent to publish, send,
spend, or merge. The blast radius scales with the permissions that
were granted.
```

# Principle 04: Verify Critical Outputs

## Statement

Outputs that drive downstream decisions must pass computational sensors
before they are acted upon. Inferential sensors supplement, never
replace, deterministic checks.

## Why this is a principle

Böckeler's taxonomy distinguishes computational sensors (type checker,
ESLint, RDKit, dependency-cruiser, Stryker, GitLeaks) from
inferential sensors (LLM-judge review prompts). The rule: prefer
deterministic. Anthropic long-running-apps uses an independent
evaluator with hard thresholds per criterion; the evaluator cannot
be the generator criticizing itself.

## What it requires

- For each deliverable, identify the critical outputs.
- For each critical output, prefer a computational sensor from
  `evals/catalog.md`.
- Inferential review is allowed but must be labelled as such.
- Independent reviewers receive only spec, artifact, evidence, and
  acceptance criteria — not the producer's reasoning chain.

# Override Protocol

H0 principles (and the invariants they map to) are defaults, not
absolutes. A project may deviate, but not silently. This protocol
defines the conditions, the recording requirements, and the
non-overridable principles.

## When an override is allowed

A principle can be deviated from only when:

1. The deviation is recorded in the project's decisions file (schema
   in `core/schemas/extension/decisions.schema.json`).
2. The decision lists the principle(s) affected.
3. The decision lists a compensating control.
4. The decision is approved by a human (`decided_by: human`).
5. The deviation is logged in the lock file or its companion
   manifest so a reviewer can audit.

## Non-overridable principles

Three principles are bedrock. They cannot be deviated from by any
layer, including the project layer, because removing them collapses
the harness's ability to function:

- **Preserve sources** — without sources, evidence provenance has no
  referent. INV-001.
- **Maintain provenance** — without provenance, claims cannot be
  distinguished from hallucinations. INV-002.
- **Expose failures** — without failure visibility, the harness stops
  learning from its mistakes. INV-009.

These map to invariants with `enforcement: locked` in
`core/invariants.yaml` and to the non-silent-weakening rule (INV-010).

## Overridable principles

The other six principles can be deviated from with the protocol
above:

- Least privilege (INV-005, INV-006)
- Verify critical outputs (INV-008)
- Maintain state (INV-003, INV-004)
- Progressive disclosure (INV-007)
- Prefer deterministic (INV-008)
- Reproducibility (INV-003, INV-012)

## Compensating controls

A compensating control is any mechanism that reduces the risk of the
overridden principle. Examples:

- For an overridden least-privilege: scope the expansion to one path,
  one task, one human approver; require a post-task audit.
- For an overridden verify-critical-outputs: add a human review
  step; require a second observer.
- For an overridden progressive-disclosure: split the entrypoint into
  nested files; validate the split with a readability test.

## Recording format

```yaml

  title: "Allow network read for literature agent"
  context: "..."
  options_considered:
    - option: "keep network denied"
      tradeoffs: "literature search is impossible"

      tradeoffs: "expands default-deny surface"
  decision: "allow network read for literature agent role only"
  rationale: "literature search is the primary capability; alternatives
    require ingesting a local corpus that does not yet exist"
  decided_by: "human:owner"
  supersedes: null
  created_at: "2026-08-29T12:00:00Z"
```

- [ ] Each override has a named compensating control.
- [ ] The compensating control is itself observable (sensor, eval, or
      human gate).
- [ ] The override expires (a duration field) or is reviewed on a
      cadence.

## Reference

See `core/principles/` for the full principle texts and the
invariant mappings.

# Autonomy Levels

Autonomy is capability-specific and bounded. A project can be L4 on
"rename files" and L0 on "submit manuscript". The universal default

| Level | Name | Meaning |

# Glossary

Terms used across the Universal Agent Harness repository and
generated project harnesses.

## Agent

An LLM-based entity that reasons and acts using a model, tools, and
context. An agent is one component of a harness; the harness
includes the controls, environment, and feedback mechanisms.

## Archetype

A reference pattern for a recurring scientific or engineering
workflow. Archetypes in `archetypes/` are documentation only; they
are NOT H1 packages and cannot be merged into a project's lock.
Promotion requires at least two real pilots and an AD.

## Bootstrap Report

The 12-section report produced at the end of dry-run discovery
(see `bootstrap/BOOTSTRAP.md` §10). Ends with `APPROVE`, `REVISE`,
or `BLOCK`.

## Bootstrap state machine

```
INITIAL → DISCOVERED → PROPOSED → APPROVED → MATERIALIZED → VALIDATED
```

Every project starts in dry-run; do not move to MATERIALIZED without
human approval when the proposal contains material scientific,
strategic, external, irreversible, permission, publication, or cost
decisions.

## Capability overlay

A cross-cutting behavior pack (e.g., scientific evidence) that
applies regardless of domain. Distinct from a lifecycle profile
and a domain pack.

## Computational sensor

A deterministic check executed by a tool: type checker, RDKit
SMILES canonicalization, schema validator, dependency-cruiser,
Stryker mutation, DOI resolver, GitLeaks. Preferred over
inferential sensors when the property is deterministically
testable (Böckeler).

## Domain pack

Domain terminology, tools, sensors, and conventions for a single
domain (e.g., computational chemistry, plant physiology).

## Evidence ledger

A durable record of claims with their sources, locations, evidence
types, and validation status. Schema in
`core/schemas/extension/evidence-ledger.schema.json`.

## Failure registry

A durable record of failures with their root causes, harness
patches, and regression sensors. Schema in
`core/schemas/extension/failure-registry.schema.json`. The harness
learns from failures by promoting them into sensors, evals, or
guides.

## Guides

Feedforward controls: specifications, instructions, constraints,
examples, architecture documents, conventions, tool descriptions.

## H0 / H1 / H2 / H3

Configuration layers:

- H0: universal invariants, defaults, schemas (this repository).
- H1: optional lifecycle profile, capability overlay, or domain pack.
- H2: project configuration and bindings.
- H3: short-lived task restrictions and context.

Resolution is typed and pinned via `core/merge-policy.yaml`.

## Harness

The environment, controls, context, capabilities, feedback
mechanisms, and limits within which an agent operates. A harness
makes correct behavior easy to perform and verify, and makes
incorrect behavior visible, recoverable, traceable, or impossible
to pass through gates.

## Inferential sensor

An LLM-judge review prompt. Reserved for properties that genuinely
require inference (semantic meaning, ambiguity, scientific
interpretation).

## Lifecycle profile

A recurring project workflow (e.g., long-running literature review).

## Lock file

`harness.lock.yaml` in a generated project. Pins the upstream
H0 version and commit, the H1 packages, the H2 project hash, and
the resolved permissions, capabilities, topology, and assurance
floors.

## Material gate

A human approval step required when a decision is scientific,
strategic, external, irreversible, publication-related, sending-
related, spending-related, or permission-expanding (INV-006).

## Permission profile

Per-agent-role capability scope. Schema in
`core/schemas/extension/permission-profile.schema.json`.

## Sensor

A feedback control. See computational sensor and inferential
sensor.

## Tool contract

A specification describing a tool's capability, input/output
schema, permissions required, side effects, failure modes, and
eval status. Schema in
`core/schemas/extension/tool-contract.schema.json`. Contracts
ship without implementations per AD-003.

## Validation vs QA vs Eval

Three distinct assurance questions:

- Validation: "Is this execution/result correct?"
- QA: "Does this artifact satisfy its requirements?"
- Eval: "Does this harness still perform across representative
  cases?"

Validation checks a single result. QA checks an artifact against
its spec. Eval checks the harness itself across a representative
test set.

# Universal Eval Catalog

Ten universal eval categories that any harness can run to verify it
still performs across representative cases. This is the menu.
`evals/bootstrap-cases.yaml` is the specific test set used to
validate this Universal Harness repository itself.

## Relationship to validation, QA, and eval

- Validation checks one execution against an oracle.
- QA checks one artifact against its requirements.
- Eval checks the harness across a representative suite.

Eval answers: "Does this harness still perform?"

## The 10 categories

### EVAL-001 — literature retrieval

- **Purpose**: verify that source discovery returns relevant sources
  with correct bibliographic metadata.
- **Input fixture**: a known topic with a known set of canonical
  sources.
- **Expected behavior**: recall ≥ 0.9 on canonical sources; all DOIs
  resolve via Crossref.
- **Metrics**: recall, DOI resolution rate, false-positive rate.

### EVAL-002 — document ingestion

- **Purpose**: verify that source files are normalized into
  agent-legible Markdown or structured form without losing content.
- **Input fixture**: a known document with known structure (PDF,
  DOCX, PPTX, XLSX, HTML, image).
- **Expected behavior**: every section heading in the source has a
  counterpart in the normalized form; tables, figures, and
  references are preserved.
- **Metrics**: section coverage, table preservation rate, figure
  reference preservation.

### EVAL-003 — structured extraction

- **Purpose**: verify that the harness extracts structured fields
  from unstructured sources accurately.
- **Input fixture**: a document with known structured fields
  (entities, claims, methods, results).
- **Expected behavior**: F1 ≥ 0.85 against the gold standard.
- **Metrics**: precision, recall, F1, hallucinated-field rate.

### EVAL-004 — numerical audit

- **Purpose**: verify that any numerical claim in the output traces
  to a computational sensor and matches the source computation
  within tolerance.
- **Input fixture**: a document with known numerical claims.
- **Expected behavior**: every numerical claim has a sensor trace;
  re-computation reproduces the source within ±1% (or declared
  tolerance).
- **Metrics**: coverage of computational sensors, reproduction rate.

### EVAL-005 — citation verification

- **Purpose**: verify that every citation resolves to a real source
  and that the cited claim is supported by the cited location.
- **Input fixture**: a bibliography with known valid and invalid
  entries.
- **Expected behavior**: 100% valid DOI resolution; 100% claim-
  location consistency.
- **Metrics**: resolution rate, false-citation rate, claim
  drift rate.

### EVAL-006 — artifact generation

- **Purpose**: verify that a deliverable artifact (report, dataset,
  code package, model card) satisfies its acceptance criteria.
- **Input fixture**: a deliverable spec with acceptance criteria.
- **Expected behavior**: every acceptance criterion passes; no
  extra-material changes.
- **Metrics**: criterion pass rate, side-effect rate.

### EVAL-007 — handoff/restart

- **Purpose**: verify that a new agent session can resume work
  from the project's state and evidence files alone.
- **Input fixture**: a project at a known state with a known next
  action.
- **Expected behavior**: the next session reads state, produces a
  plan consistent with the recorded next action, and continues.
- **Metrics**: plan fidelity, reproducibility, time-to-resume.

### EVAL-008 — agent coordination

- **Purpose**: verify that a multi-agent topology (Level C/D/E)
  coordinates without dropping or duplicating tasks.
- **Input fixture**: a task DAG with known dependencies.
- **Expected behavior**: every task is assigned exactly once;
  every dependency is honored; the final artifact is a union of
  the parts.
- **Metrics**: assignment rate, dependency-respecting rate, lost-
  update rate.

### EVAL-009 — conflicting-source resolution

- **Purpose**: verify that the harness reconciles conflicting
  sources by recording both, distinguishing them, and resolving
  with explicit rationale.
- **Input fixture**: a topic with two known contradictory sources.
- **Expected behavior**: both sources are recorded; the conflict is
  flagged; a resolution is recorded in `decisions.schema.json` or
  the output.
- **Metrics**: source coverage, conflict detection rate, resolution
  explicitness.

### EVAL-010 — failure recovery

- **Purpose**: verify that a controlled failure is recorded, the
  repair path executes, and the harness resumes from the rollback
  point.
- **Input fixture**: a synthetic failure injected at a known point.
- **Expected behavior**: failure-registry entry created; repair
  attempt succeeds within retry budget; observability-run shows
  the failure and the recovery.
- **Metrics**: time-to-detect, time-to-repair, recovery success
  rate, regression-sensor coverage.

## When to use

- The human has just declared a new project.
- The human wants to know which archetype, capabilities, and tools

- The agent is preparing a Bootstrap Report and needs the
  classification as input.

## When NOT to use

- The project already has a `project.yaml` and a `harness.lock.yaml`.
- The classification has already been recorded.
- The project is being maintained, not bootstrapped.

## How to run

1. Read `skills/classify-project/questions.md`.

   logic.

5. Map the answer set to a recommendation.
6. Fill in `skills/classify-project/output-template.md`.

- **Do not modify the target project.** Classification is read-only
  with respect to the project workspace.

# Tool Contracts

YAML specifications of agent-invokable tools. Each contract describes
what a tool does, what it requires, and what it returns. **No
implementations ship in v0.3.0** (AD-003, AD-009).

## What a contract gives an agent

A contract tells the agent:

- which capability the tool provides;
- which inputs the tool accepts and which outputs it produces;
- which permissions the tool requires;
- which side effects the tool has;
- which failure modes the tool exhibits and how to detect and recover
  from each;
- the current `eval_status` (untested at v0.3.0 launch).

A contract does NOT tell the agent:

- how the tool is implemented (Python, Bash, MCP, HTTP);
- where the tool runs (local, container, cloud);
- whether the tool is currently available.

## Relationship to schemas

Every contract here conforms to
`core/schemas/extension/tool-contract.schema.json`. The validator
(`scripts/validate_repo.py`) parses each contract against that
schema.

## Promotion path: contract → implementation

1. At least two real projects reference the contract in their
   `harness.lock.yaml` capability list.
2. The contract's `eval_status` field has been moved from `untested`
   to a documented state after a pilot.
3. An AD records the promotion and the implementation language.
4. The implementation lands in `scripts/` (or a designated tool
   location) at v0.4.0+.

Until then, the contract is a planning artifact, not a callable.
